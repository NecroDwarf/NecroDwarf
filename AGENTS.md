# AGENTS.md — NecroDwarf Website (отдельный репозиторий)

## Назначение

NecroDwarf — независимая команда разработчиков игр, сервисов, приложений и инструментов. Этот репозиторий содержит **сайт команды**, а не Minecraft-мод Maniac. Язык основного интерфейса — русский. Названия продуктов и ники не переводить.

Этот файл содержит **постоянные правила**, а не автоматическое поручение разрабатывать новые функции. Конкретный объём задаёт текущее сообщение пользователя и `NECRODWARF_V2_TZ.md`. Работать только над указанным этапом.

## Дизайн

- Утверждённая основа сайта — **Neo Tech V2 / Jade Engineering**.
- Слоган: **«Куём идеи. Оживляем код.»**
- Фирменный Jade — `#00A86B`; дополнительные цвета: `#176B50`, `#53CFA1`, `#090E0C`, `#17211C`, `#B69A62`, `#E7E2D4`, `#9CAEA2`.
- `Necro` — нефритовая некромантия, `Dwarf` — камень, металл, бронза, кузница, руны. Сайт должен оставаться современным технологичным портфолио, а не средневековым интерфейсом.
- Каждый проект может иметь собственные визуальные акценты; каждый релиз может иметь собственную тему. Цветочное обновление Flower Cleaning остаётся цветочным.
- Утверждённый логотип будет прикреплён позднее: **не придумывать и не генерировать новый**, не считать эмблему из старого прототипа окончательной. Пока использовать аккуратный текстовый wordmark и компонент `BrandLogo`.

## Продукт и материалы

- Только три проекта в новом публичном каталоге: **Maniac, FriendSheep, NovellMaker**. На главной и в каталоге они равноправны. Старые замороженные проекты не выводить.
- Общая `/changelog` — лента последних выпусков всех проектов; собственные хроники — внутри каждого проекта; единый источник метаданных без дублирования.
- Maniac Wiki задумана как полностью открытая энциклопедия, включая точные характеристики и секреты. Не подменять проверенный баланс догадками.
- Контент через GitHub/Codex, без CMS и обязательного бэкенда.
- Отдельные страницы и ресурсы проектов должны находиться в соответствующих папках. Общие UI-компоненты, темы и утилиты вынести отдельно.
- Исходные старые материалы Maniac можно **читать** в старом репозитории, но нельзя изменять его без прямой команды пользователя.

## Технические принципы

- React + TypeScript + Vite; статическая генерация опубликованных страниц; Cloudflare Pages с собственным доменом.
- Для длинных материалов — MDX; для типизированных характеристик/метаданных — TypeScript; изолированные стили — CSS Modules и CSS variables.
- Предпочитать простые поддерживаемые зависимости, не добавлять API, CMS, Workers/SSR, аккаунты или другие инфраструктурные сервисы без конкретной необходимости.
- Не смешивать стили проектов; не превращать весь сайт в гигантский файл со множеством условий.
- Обеспечивать доступность (семантика, контраст, навигация с клавиатуры, фокус, alt, reduced motion) и адаптивность.
- Не включать заглушки и черновики в публичную навигацию/sitemap.

## Рабочие правила (адаптированы из AGENTS.md Maniac)

1. Перед изменениями **читать относящиеся к задаче файлы** и изучать текущее состояние git.
2. Менять **только то, что входит в задачу**. Не запускать будущие этапы «заодно».
3. **Не откатывать и не перезаписывать чужие изменения** без явной команды пользователя.
4. Ошибки вне текущей задачи не чинить молча: сообщить о них и предложить отдельное исправление.
5. Если решение неоднозначно, использовать уже утверждённые договорённости; если их недостаточно, явно отметить допущение/риск и не маскировать домыслы под факты.
6. Предпочитать существующие согласованные архитектурные паттерны; для ручных исправлений применять точечные патчи, по возможности `apply_patch`.
7. Не менять секреты, `.env`, deployment credentials и несвязанные/generated файлы.
8. Проверять итоговый `git diff` и статус, чтобы в изменениях были только относящиеся к задаче файлы.
9. Запускать разумный минимум проверок (typecheck, build, нужные тесты/линтер); конкретно называть неудавшиеся проверки и причины.
10. В финальном отчёте перечислять изменения, команды, результаты проверок, известные ограничения и то, что сознательно осталось на следующий этап.
11. Не выполнять деплой на production, не переключать домен и не менять исходный GitHub Pages-сайт без прямой команды.
